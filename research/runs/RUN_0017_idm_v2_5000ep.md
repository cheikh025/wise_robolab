## Purpose

- exact question this run answers: RUN_0015 showed the v1 architecture (1537-token flatten-to-grid encoding) plateaus at val_mean_joint_mae=0.11701 at 5000-episode scale even with a properly matched 30-epoch budget -- worse than the 500-episode checkpoint (0.06857), a genuine capacity/token-efficiency problem. Does v2 (spatial-softmax token compression to 96 tokens, vision-only/no proprio, per EVA arXiv:2603.17808 and VPT arXiv:2206.11795-informed redesign) resolve this and beat both RUN_0015 (same data, old architecture) and ideally RUN_0009 (500ep, old architecture, still the best checkpoint overall)?
- pass/fail criterion: val_mean_joint_mae meaningfully below RUN_0015's 0.11701 (redesign helps at this data scale) -- bonus/stretch goal: below RUN_0009's 0.06857 (redesign fully closes the gap and lets 5000 episodes actually pay off).
- why this task/data budget is sufficient for this validation: identical 5000-episode data/split to RUN_0012/13/15 (already downloaded, cached, verified) -- an apples-to-apples architecture comparison, same epoch budget (30) as RUN_0015 for a fair comparison.

## Code state

- repo: `/workspace/wise_idm`, git commit `888dfca` (dream-inference script) + this run's new files
- new files: `model_v2.py` (`DroidIDMv2`, `SpatialSoftmax`), `train.py` updated with `--arch v1|v2` dispatch (`call_model()` helper, arch-conditional model construction, checkpoint config now records `arch`/`num_keypoints`)
- relevant design decisions (from extended discussion, see conversation record / `STATE.md`): keep CNN backbone + adjacent-pair fusion + global non-causal transformer + learned-query decoder + joint/gripper heads unchanged; replace flatten-to-16-tokens-per-pair with spatial-softmax-to-1-token-per-pair (1537->96 tokens); drop the proprioception token entirely (pure vision, matching EVA/VPT); deliberately did NOT add VPT's wider local-temporal-conv (reasoned that pair-token-level attention already gives a comparable path to cross-step motion info, revisit only if a specific failure mode shows up).
- validated pre-run: v2 overfit-test on a tiny 4-episode debug subset converged cleanly (loss 1.62->0.004, gripper_acc->100%, joint_mae->0.033 over 300 steps, 14.5s) confirming the whole pipeline (model/loss/training loop/checkpoint) works before committing to the real run. Batch-size calibration (see below) confirmed v2 trains correctly at 500-episode scale too (1 epoch, 58.3s, val_mean_joint_mae=0.207).

**Batch-size calibration** (applying the lesson from RUN_0015's initial batch=16 underutilization, this time checked *before* committing to the long run): tested batch=96/GPU first -- 75135MiB/81920MiB (94%), too tight, killed pre-epoch-completion (near-zero sunk cost).
